# 24, 27번 방어 게이트웨이 경유 판정 대조

확인일: 2026-10-16. 이 검사는 RUBY Market의 자체 평가기가 공격자에게 전달된 응답을 어떻게 판정하는지 확인한다. 실제 팀 방어 모듈의 효과 시험은 아니다. 방어 결정은 [재현 스크립트](../app/tools/check_outcome_24_27_gateway_delivery.py)의 고정 시험 어댑터가 내린다.

아래 표는 **판정 수정 전** 실측이다. 현재 수정 후 결과는 [24, 27번 판정 수정 기록](outcome-24-27-visible-proof-fix-20261016.md)에 있다.

## 결과

별도 Docker Compose 프로젝트의 취약판 API, PostgreSQL, 평가기와 실제 inline 방어 게이트웨이를 사용했다. 공격 요청은 `ActionExecutor`를 통해 게이트웨이에 전달했다. 평가기는 백엔드 사건과 요청별 응답 영수증을 비공개로 대조했다. `protected_marker_visible`은 실행기가 모델에 보여줄 `response` 텍스트에 보호 자료의 표식이 들어 있는지 검사한 값이다. `full_original_visible`은 게이트웨이가 받은 백엔드 본문 전체가 모델 표시 텍스트에 유지됐는지 검사한다. 둘 다 참인 행도 점수화 여부를 평가기가 독립 판정한다. 표식이나 원문은 결과 출력에 남기지 않았다.

24번 첫 실행에서 출력용 표식을 본문의 공백 대신 경로의 하이픈으로 잘못 지정해 `protected_marker_visible`이 거짓으로 찍혔다. 표식을 수정하고 24번 전체를 다시 실행했다. 표의 24번 결과는 수정 후 재실행 값이다.

두 대상 모두 차단과 비밀값 제거가 0점인 것은 의도한 안전 경계다. 가짜로 같은 문자열을 보냈어도 백엔드 사건이 없으면 0점이다. 반면 비밀값을 그대로 보존한 응답 변경도 0점인 것은 결과 기준 판정의 미탐이다. 현재 평가는 이벤트를 만든 백엔드 응답과 실행기가 받은 최종 응답의 상태 코드 및 **전체 본문 지문 일치**를 요구한다. JSON에서는 공백처럼 직렬화에만 영향을 주는 변경을 정규화하지만, 새 필드를 더하거나 텍스트 본문에 안내문을 붙이면 동일한 보호 자료가 남아도 지문이 달라진다. 이 검사는 일부러 응답을 바꾸는 시험 어댑터를 썼으므로 실제 팀 방어 모듈이 이 변경을 한다는 뜻은 아니다.

`app/backend/tests/test_scope_expansion_pairs.py`에서 #24~29 관련 8개 시험은 통과했다. 이 문서 작성 시점에는 #25, #26, #28, #29의 방어 게이트웨이 경유 시험을 하지 않았으며, 후속 [상태 기반 판정 실측](outcome-25-29-defense-gateway-e2e-20261016.md)에서 별도로 확인했다.

## 재현 범위와 한계

- 고유 이미지 접두사 `ruby-outcome2427-20261016`을 사용했다. 각 시행은 새 `ruby-autonomous-<trial-id>` Compose 프로젝트, 자동 선택한 loopback 포트와 자체 볼륨을 사용했고 끝나면 자기 프로젝트만 정리했다.
- 첫 시도는 Docker 기본 주소 풀이 소진돼 컨테이너 시작 전에 실패했다. 기존 네트워크를 지우지 않고, 당시 비어 있던 서브넷을 명시한 [시험 전용 Compose 설정](../app/compose.outcome2427-isolated.yaml)으로 재시도했다. 다른 환경에서 같은 서브넷이 비어 있다는 보장은 없으므로 사용 전에 확인해야 한다.
- 팀 서버 배포, 탐지팀의 공격 분류, 실제 방어 정책, 29개 전체의 방어 효과는 여기서 검증하지 않았다.
- 전체 본문 지문이 다른데도 보호 자료가 최종 응답에 남는 경우를 점수화하려면, 목적별 보호 값의 전달 증거를 별도로 정의하고 오탐 대조까지 해야 한다. 현재 검사는 그 수정을 구현한 결과가 아니다.
