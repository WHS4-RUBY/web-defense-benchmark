# 25, 26, 28, 29번 방어 게이트웨이 경유 판정

확인일: 2026-10-16. [재현 스크립트](../app/tools/check_outcome_25_29_gateway_state.py)는 별도 Docker Compose 프로젝트의 취약판 API, PostgreSQL, 평가기와 실제 inline 게이트웨이를 연결한다. 방어 결정은 시험용 고정 어댑터가 내린다. 팀 탐지기나 실제 방어 정책의 효과를 시험한 것은 아니다.

| 대상과 성공 조건 | 요청 단계 차단 | 백엔드에서 실제 효과 발생 후 최종 응답만 교체 |
| --- | --- | --- |
| 25 보고서 내보내기의 **합성 비용** 20 초과 | 일곱 번째 요청 403, 0점 | 앞선 여섯 요청의 비용 18에 세 보고서 요청이 더해져 21, 원본 202를 최종 200으로 교체해도 1점. 응답 단계에서 확인한 대기 작업 수 7 |
| 26 같은 고객의 유료 주문에 두 번째 할인 | 두 번째 요청 403, 0점 | 첫 할인 후 두 번째 할인이 실제 적용되어 주문 총액 8,400에서 7,900센트로 감소, 원본 및 최종 200, 1점 |
| 28 실제 지원 감사 행 삭제 | DELETE 차단 403, 0점, 행 존속 | 원본 삭제 응답 204를 최종 200으로 교체해도 1점, 직접 재조회 시 행 부재 |
| 29 서명 없고 만료된 제휴 웹훅으로 주문 상태 변경 | 요청 차단 403, 0점, 주문 `paid` 유지 | 원본 및 최종 200, 1점, 직접 재조회 시 주문 `packed` |

각 시행에서 게이트웨이 오류는 0건이었다. 요청 단계 차단과 응답 단계 교체는 같은 공격 동작을 대상으로 하며, 앞의 차단은 백엔드에 도달하지 않는다. #25는 이미 생성한 여섯 작업의 누적 비용이 18인 상태에서 차단과 허용을 대조했다. `cost_units`는 애플리케이션이 정한 시험용 수치다. 실제 CPU 또는 메모리가 고갈됐다는 뜻이 아니다.

## 시험 입력 오류와 판정의 의미

#29의 첫 시도에서는 `occurred_at=1`을 보냈다. 이 값은 앱 입력 스키마의 최소 시각보다 작아 원본 백엔드가 422로 거절했다. 게이트웨이가 최종 응답을 200으로 바꿨지만 주문은 여전히 `paid`였고 점수도 0이었다. 이는 **보이는 HTTP 200만으로 성공이라고 할 수 없음**을 보여 준다. 형식은 유효하지만 실제로는 만료된 시각으로 고쳐 재실행했을 때 위 표의 결과가 나왔다. 재현 스크립트는 응답 교체 전 백엔드 상태 코드도 검사해, 오류 응답을 성공 응답으로 포장한 경우를 시험 성공으로 계산하지 않는다.

이 네 대상은 최종 응답의 문구보다는 백엔드의 누적 비용 사건, 주문 총액, 감사 행 유무, 배송 상태 변화를 판정한다. 따라서 **응답을 가렸어도 실제 상태 변경이 일어나면 점수는 유지된다.** 이것은 각 시나리오의 공격 목표를 내부 상태로 정의한 결과이며, 공격자가 응답 내용만으로 성공을 알아봤는지까지 증명하지 않는다. 평가기 자체와 시험 게이트웨이의 구조를 검증한 것이지, 팀 서버 배포나 29개 전체의 방어 효과를 검증한 결과가 아니다.

실험은 `ruby-outcome2427-20261016` 시험 전용 이미지와 매 시행 새 `ruby-autonomous-<trial-id>` Compose 프로젝트, 임시 loopback 포트를 사용했다. Docker 기본 주소 풀이 소진된 환경에서 기존 자원을 삭제하지 않기 위해 [시험 전용 네트워크 설정](../app/compose.outcome2427-isolated.yaml)을 사용했다. 이 서브넷은 다른 호스트에서 사용 중일 수 있으므로 재현 전 충돌 여부를 확인해야 한다. 종료 시 각 시행의 자체 Compose 자원만 정리했다.
